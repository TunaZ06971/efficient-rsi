# 做题记录卡，以及做题前的两种 SIFT

这版代码做三件事：把一次做题发生了什么记清楚；用固定程序检查子代；让本地 Qwen 给子代打分，HGM 用这个分数排"先测谁"。**只接在子代生成后、正式评测前，父代选择规则没有改。只有程序查出"肯定启动不了"才会跳过子代；Qwen 从不跳过子代，只影响先后。SIFT 默认关闭；打开后默认先记判断、照常做题。**

**记录卡也默认关闭（`HGM_TASK_RECORDS=1` 才打开）。** 不打开时，`polyglot/harness.py` 跑的就是 efficient-rsi 原来的评测代码，一行没改：新代码只在函数开头多了一行分流，记录卡版本是另外的函数。打开以后评分规则也和原来一样，判分那几行是从原函数原样复制的（见第 4 节）。

## 1. 放在整个流程的哪里

```text
沿用 HGM / DGM 原来的办法选父代
            ↓
根据父代已有的做题记录修改代码，生成子代和 diff
            ↓
SIFT：读改动前后代码、diff、运行条件、父代已有记录
            ↓
仅观察：保存建议，照常做题
实际执行：程序查出肯定启动不了 → 保留代码和判断，不派题；
          其余子代照常做题，HGM 按 Qwen 分数的排名决定先给谁派题
            ↓
做了题的子代：保存每道题的记录卡，沿用原来的评分、搜索流程
```

这里有两个不同的文件：子代目录的 `model_patch.diff` 是“怎样改 Agent 的代码”；记录卡里的 `submitted.diff` / `workspace.diff` 是“Agent 做某一道题时写出的答案”。SIFT 看前一种。子代还没做题，不能拿后一种当预测依据。

## 2. 程序 SIFT 怎么工作

代码在 `sift.py` 的 `build_input()`、`program_judge()`。

程序先从本轮实际使用的初始代码出发，按顺序套上祖先补丁和新补丁，在临时目录还原出父代、子代代码。它只读代码，不运行子代、不调用模型。

程序只在"肯定启动不了"时建议跳过。前五条由 `startup_facts()` 从子代的**全部**代码里查（不受给 Qwen 的输入预算限制），后几条只提醒：

| 看到了什么 | 程序的结论 | 是否建议跳过 |
|---|---|---|
| 实际启动的入口文件被删掉 | 启动文件不存在 | 是 |
| `coding_agent.py` 没有 `if __name__ == "__main__":` | 启动后什么都不做 | 是（原版 Agent） |
| `coding_agent.py` 的 argparse 接不住评测固定传入的参数（`--problem_statement` 等 9 个），又没用 `parse_known_args` | 一启动就报错退出 | 是（原版 Agent） |
| 某个 `tools/*.py` 没有 `tool_info` 或 `tool_function` | `load_all_tools` 报错被吞掉，模型一次都不会被调用 | 是（原版 Agent） |
| 启动时会加载的文件有语法错误：入口、每个 `tools/*.py`、以及它们在模块顶层（不在 try/if/def 里）import 的本仓库文件 | Python 一启动就报错 | 是 |
| 不会在启动时加载的文件有语法错误 | 未必会运行到 | 否，只提醒 |
| 新增了循环 | 可能多花时间，也可能有帮助 | 否，只提醒 |
| 测试隐藏的环境里新增测试命令 | 要确认它是否自己准备了测试 | 否，只提醒 |
| 还原出的代码与父代完全相同 | 代码没变，重复测试仍可能提供统计信息 | 否，只提醒 |
| 补丁无法还原、关键文件没读到 | 证据不足 | 放行，保存原因 |

例如把 `def solve():` 改成 `def solve(:`，电脑自己就能知道括号坏了，无需让 Qwen 再猜一次。但把“尝试一次”改成“尝试三次”，程序只知道次数增加，**不知道额外尝试能不能换来更多做对的题**。

**在 v1 上核对过（就是这份 `startup_facts()` 代码）：** efficient-rsi v1 的 413 个子代（去掉并发 bug 清空的 8 个节点和它们的子孙），按账本有 73 个一次模型都没调用过。这份程序抓到其中 66 个，能正常调用模型的 340 个子代一个都没被判成"启动不了"。旧版只查前两条，只抓到 8 个。这些子代几乎不花做题时间，所以跳过它们主要是让账本和搜索树更干净，省下的 GPU 很少。

little-coder 的入口和工具注册表被冻结（`lc_integration.FROZEN`），所以只查语法。语法检查用 `feature_version=(3, 11)`（做题容器是 Python 3.11）；宿主机 Python 低于 3.11 时，语法问题只提醒、不跳过。成本预测器没有搬过来。

## 3. Qwen SIFT 怎么工作

代码在 `sift.py` 的 `qwen_judge()`、`ab_probability()`。

两种评委拿到同一份 `input.json`：改动前后代码、diff、实际入口、做题时间限制、是否能看到官方测试，以及最多四份有代表性的父代记录摘要。程序的启动检查结果和文件指纹不发给 Qwen，免得它照抄程序的结论。

**计费：** 开着账本（设了 `RSI_LEDGER`）时，评委请求和做题、改壳一样经过 efficient-rsi 的计量代理（`RSI_PROXY_URL`），标签是 `sift`，账本里有对应的 `llm_call`，`analyze_ledger.py` 会把它列成单独一行。代理原样转发请求体，所以 A/B 的 logprobs 照样拿得到。开着账本却没设代理，或者同时设了会绕开代理的 `SIFT_BASE_URL`，搜索启动时就报错。请求里关掉了"先思考"（`enable_thinking: false`），不然会先思考的模型第一个词读不到 A/B。父代没有新记录卡时，历史部分为空，不编造记录。文件超出输入预算会标明省略；重要的子代文件没装下时，这次打分不用于排序。

输入预算是 8 万字符，装文件的顺序是：先装每个改动文件的**子代版本**（真正要运行的代码），再装父代版本，最后装没改的参考文件各一份。每个文件的指纹留给程序检查，不发给 Qwen。little-coder 的冻结文件（`hgm_agent.py`、`rsi_record.py`、`providers.py`、`tool_registry.py`、`config.py`，见 `lc_integration.FROZEN`）补丁过滤器不允许子代改，所以不占预算。实测：一个同时改 `tools.py`、`agent.py`、`harness_knobs.json` 的 little-coder 子代，父代带四张记录卡时，发给 Qwen 约 7.9 万字符，子代的完整 `tools.py` 装得下（父代版 `tools.py` 装不下，改动内容靠 diff 看）。补丁很长时仍可能装不下，那样这个子代就按没有分数处理。

Qwen 收到的要求是：

> 第一项回答 A 或 B。A 表示值得花预算测试，B 表示建议跳过。然后用一小段话解释。证据不够时选 A。

**只发送一次请求**，同一份回复拿到：

- 第一个位置上 A、B 的 token 概率；
- 后面的简短解释；
- 这次请求返回的 token 用量、请求耗时。

例如，模型在第一个位置给 A 的概率是 0.08，B 是 0.32，其余词合计 0.60。只在 A/B 两个选项里比较，A 的分数是 `0.08 / (0.08 + 0.32) = 0.20`。**这表示模型在两个选项之间更偏向 B，不代表这个子代只有 20% 的做题正确率。**

**分数只用来排先后，不用来砍子代**（`order_priors()`，HGM 的 `sample()` 里使用）。HGM 每次派题前，按"做对几道、做错几道"给每个子代抽一个数（Thompson 采样），抽到最大的先做下一道。打开排序后：

- 只看这个子代的分数在**所有打过分的子代里排第几**（中位排名百分位 q），不用原始分数。原始 A/B 分数没有校准；如果 Qwen 给谁都打高分，按排名算平均 q 仍是 0.5，打过分的子代整体不会因此多拿题。
- 排名换算成 `SIFT_ORDER_WEIGHT` 道"虚拟题"（默认 2）：排名 q 的子代，开局像是多做了 2 道题、对了 2q 道。只有一个打过分的子代时 q = 0.5，等于没有影响。
- 真实成绩照常累加，几道题之后以真实成绩为主。按同一公式模拟两个新子代（排第一和排第二）：没有排序时先测谁各占 50%；打开后排第一的先被选中约 79%；两人都做了 5 道、都对 2 道时约 69%；如果排第二的 5 道对 3 道、排第一的只对 1 道，排第一的只剩约 31%。
- 没有可用分数（服务不可用、关键代码没装下、只记录模式）的子代虚拟题为 0，和原来完全一样。所有子代都没分数时，采样与原来逐位相同。
- 父代选择（`expand()` 里的采样）没有改。DGM 每生成一个子代就立刻做完它的小题组，没有排队等测的子代，所以 DGM 里分数只记录、不起作用。

权重 2 是试点值，没有用数据校准过。

解释是模型给出的理由，不是已经证实的因果证据。一次请求也不是零成本：读代码、生成解释都花模型时间，必须计入总账。

以下情况这次打分都不用于排序，并记录原因：服务连不上、不支持所需概率字段、第一项不是 A/B、没有同时拿到 A 和 B 的概率、关键输入缺失。尤其不能把“返回结果里没有 B”当作“B 的概率为零”。

只允许 `localhost` 或私有/回环 IP 的本地 vLLM 地址，不读取系统 HTTP 代理，不跟随重定向；没有接外部付费模型 API。`SIFT_MODEL` 是服务端实际注册的模型名，需要与部署一致。

vLLM 的接口字段依据[官方兼容服务文档](https://docs.vllm.ai/en/stable/serving/online_serving/openai_compatible_server/)。不同部署版本需实测；可选 `SIFT_AB_TOKEN_IDS` 只在确认当前 tokenizer 的 A/B token ID 和服务端支持后填写，不能照抄别的模型的 ID。

## 4. 记录卡记了什么

代码在 `task_records.py`；原版 Agent 和 little-coder 的收卷接入都在 `polyglot/harness.py`。

| 内容 | 大白话 |
|---|---|
| 身份 | 哪个运行、哪个版本、哪个父代、哪道题、这是第几次尝试的唯一编号 |
| 运行条件 | 模型、初始代码指纹、祖先补丁指纹、题目版本、时间上限、测试可见性 |
| 执行结果 | 正常返回、被时间上限杀掉、轮数用完、主动到时停止、异常；不能确定就写未知 |
| 已有答案 | 它主动交的答案，以及停下来后从允许的答案文件里收回的改动 |
| 判分结果 | 是否真正进入判分、测试命令退出码、判分超时、测试完整性 |
| 测试数量 | 日志里能明确读出的通过、失败、跳过数量；读不出就写未知 |
| 花费 | 各阶段经过时间、已记录的模型请求数、token、回放数和统计覆盖范围 |
| 证据 | 轨迹、额外轨迹、输出日志、判分日志、little-coder 请求记录 |
| 资料缺口 | 哪个文件没收回来、哪些字段还不知道 |
| 原来的结果 | 保留原来的 `eval_result`，方便对照旧评分 |

**“为什么停”和“答案对不对”分别记录。** 一个 Agent 被限时杀掉，但收回的答案通过测试，可以同时记为“硬超时”和“答案通过”，不能为了记通过就抹掉超时。

每次尝试都有新目录，重试不会覆盖上次的卡：

```text
<run>/<child>/
├── model_patch.diff
├── sift/
│   ├── input.json                 # 两种评委实际看到的同一份材料
│   └── decision.json              # 判断、理由、概率、模型原始回复和请求用量
└── predictions/<evaluation>/
    ├── <task>.json                # 兼容旧流程，指向本次记录卡
    └── task_records/<task>/<attempt-id>/
        ├── card.json
        ├── submitted.diff         # 若成功收到了主动提交的答案
        ├── workspace.diff         # 若成功收回了允许的答案文件改动
        ├── trajectory.md          # 若成功收到了轨迹
        ├── grading.log            # 若实际执行了判分
        └── legacy_result.json
```

**评分和不开记录卡时一样。** 判分的几行是从 `process_entry` 原样复制的，暂存答案仍然是 `git stash push <答案文件>`。另外，凡是原代码会记"没做完"的情况，`patch_for_grading()` 都会抛异常，结果同样记"没做完"：做题程序退出码不是 0、对话记录或补丁读不到、little-coder 没有 `rsi_attempt.json`。补丁和原代码一样，在容器里用 `cat` 读，所以容器里的符号链接只会在容器里解析。其他从容器拷出来的文件，如果是符号链接就拒收、记一条收集错误。原因是 Docker 的 tar 导出会把链接原样还原到宿主机上，读它就会读到宿主机自己的文件。

收卷发生在切换测试代码和清理容器之前。宿主机会先尝试停止做题容器里遗留的写入进程；无法确认停止时，不使用不稳定的答案快照。新旧答案只收基准允许的 solution 路径。

**磁盘：** 记录卡目录在 `<节点>/predictions/<节点>_0/task_records/` 下，会把这道题已有的几份日志各再存一份：做题记录、判分日志、`<题>_docker.log`、做题程序的输出。所以开着记录卡时，这些文件的占用大约翻倍（压缩前）。`run_all.sh` 的 `compress_outputs` 会压缩 `*/predictions/*` 下大于 1 MB 的文件，记录卡目录也在其中。没有改用硬链接，因为 gzip 会跳过有其他硬链接的文件，那样反而压不了。

**开跑前怎么估：** 冒烟测试后，用 `du -sk <某次评测的记录卡目录>` 量出每次评测的增量，乘以一次搜索的评测次数（v1 约 800），再乘以并行的搜索数。家目录剩余空间要能放下一次搜索在压缩前的全部增量。

`HGM_RECOVER_ANSWERS=0` 时，超时后的答案会保存，但不改变原来“未完成”的评分。设为 `1` 才让这些收回的答案进入正式判分。评分使用容器中的答案工作区，diff 是保存下来的证据。这个开关要在比较的各组保持一致。

`HGM_RECORD_FEEDBACK=1` 时，下一次改代码可以看到不同失败类型的记录摘要；选择重点失败题时也纳入超时、异常等类别。它改变的是“给提议者看哪道题”，**不是“选哪个父代”**。提供了哪些记录会另存清单；这只能证明模型拿到了材料，不能证明它认真读了。

## 5. 现在可以直接看的演示

在仓库根目录执行：

```bash
python3 repos/HGM/sift.py --demo --mock-qwen --explain
```

这个演示故意写坏入口函数的括号：

1. 程序找出第一行语法错误，建议跳过。
2. **虚构的 Qwen 回复**为 B，A/B 相对分数约 0.1，并附一句解释。Qwen 的结论永远是"照常测"，分数只用于排序。
3. 演示只展示建议，不跳过任何真实评测。

`--mock-qwen` 完全不调用模型。这个数字是写死的示例，不能用作 Qwen 有效性的证据。若要保存输出，加 `--output /某个绝对路径/演示.json`。

## 6. 怎么打开与怎么比较

以下是运行环境开关，不会自行启动 GPU 服务或实验：

| 设置 | 实际行为 |
|---|---|
| `HGM_TASK_RECORDS=1` | 打开记录卡；默认 0，评测代码就是 efficient-rsi 原来的那份 |
| `SIFT_MODE=off` | 默认：不调用两种评委。写成别的值（不是 off/program/qwen/compare）时，搜索启动就报错 |
| `SIFT_MODE=program` | 只跑固定程序 |
| `SIFT_MODE=qwen` | 先跑固定程序（免费）；程序没判死的子代再请求一次本地 Qwen 打分 |
| `SIFT_MODE=compare` | 两者都判断，永远照常做题、不排序，用于对照建议与真实结果 |
| `SIFT_ENFORCE=0` | 默认：保存建议，不跳过、不排序 |
| `SIFT_ENFORCE=1` | program / qwen 模式中，程序查出肯定启动不了的子代被跳过（不再请求 Qwen）；qwen 模式中 HGM 按分数排名排序。Qwen 从不跳过子代；compare 模式仍只记录 |
| `RSI_LEDGER` + `RSI_PROXY_URL` | 开着账本时，评委经计量代理（标签 `sift`）；缺代理就在启动时报错 |
| `SIFT_BASE_URL=http://127.0.0.1:8000/v1` | 只在没开账本时用（本地测试、演示）的 vLLM 地址；开着账本时必须不设 |
| `SIFT_MODEL=vllm-qwen3c-local` | 默认服务模型名，需要与部署核对 |
| `SIFT_ORDER_WEIGHT=2` | Qwen 排名折算成几道"虚拟题"；0 表示不排序；未校准的试点值。写错（负数、非数字）在搜索启动时报错 |
| `SIFT_REQUEST_TIMEOUT=90` | 评委请求等待上限，秒 |
| `HGM_RECOVER_ANSWERS=1` | 对异常停止后收回的答案判分；默认 0。要同时设 `HGM_TASK_RECORDS=1`，否则启动时报错 |
| `HGM_RECORD_FEEDBACK=1` | 下一轮改代码使用更完整的失败反馈；默认 0。同样要 `HGM_TASK_RECORDS=1` |

已有 `input.json` 可以单独送给已启动的本地 vLLM：

```bash
SIFT_BASE_URL=http://127.0.0.1:8000/v1 \
SIFT_MODEL=vllm-qwen3c-local \
python3 repos/HGM/sift.py --input /某个子代/sift/input.json --mode compare --explain
```

正式试跑用新的输出目录和新的 `--initial_agent_name`，让初始化重新复制本次代码。不要直接复用旧的初始 Agent 缓存来声称验证了新的 little-coder 停止原因记录；旧缓存里的适配器可能还没有新增字段。也不要把已有成绩接在新协议下面继续算。

真正打开 `SIFT_ENFORCE=1` 时，搜索还要求正数、有限的 `--max_hours`。因为跳过测试不消耗题数预算，却仍然消耗生成子代和审阅的时间；只设题数上限可能不断生成、不断跳过。时长上限沿用现有搜索的“到时不启动新工作”机制，不会强行切断已在进行的任务。

建议下一步依次做：

1. **先看演示和改动。** 明确每条规则到底在断言什么，所有代码由你自己提交。
2. **有空闲算力时跑小试点。** 新建实验，先用 `SIFT_MODE=compare`，每个子代都真正做题。检查记录是否收全、真实 vLLM 是否同时返回 A/B 概率、评分是否合理。
3. **再看误伤和排序准不准。** 程序建议跳过的子代，实际能做对多少题、总共花多久？Qwen 分数排名和子代真实成绩的排名对不对得上？Qwen 的判断成本也要加进去。先量这个，再决定排序权重，不先宣称它更强。
4. **最后做三组实验。** 无 SIFT、程序 SIFT、Qwen SIFT。固定模型、题目、预算、收卷开关、反馈开关、父代选择设置；使用多个种子比较同预算下最终版本在留出题上的表现。不要一边加记录反馈、一边加 Qwen，然后把全部提升归功于 Qwen。

更全面的反馈确实可能帮助 Qwen，例如父代经常在反复重试后超时，新补丁增加了更早交卷的机制，Qwen 可以尝试判断改动是否对症。但程序也能从同样的记录读出超时次数和用量。换题库时，语法等程序规则依然通用；Qwen 也可能误解新测试协议。**在旧题库选好规则、提示词和排序权重，在新题库冻结使用，再比较误伤、总成本和最终成绩，才能知道谁更能适应新题库。**

## 7. 验证范围和明确局限

- 本地 `instrumentation/tests` 全部通过（数量见 PR 说明），其中包括：开关关着时 `process_entry`、`process_entry_lc` 发给容器的命令和写出的结果与 efficient-rsi 原函数完全一样；打开记录卡后，各种退出情况下的评分结果也和原函数一样。`erl/` 的测试也通过。排序部分只测了打分换算和开关逻辑，HGM 主循环里的接入没有单独的自动测试。收卷测试用假容器；补丁还原和答案路径限制用真实临时 Git 仓库；请求协议用本地假 HTTP 服务。
- 命令：`uv run --no-project --python /opt/homebrew/bin/python3.12 --with numpy --with scipy python -m unittest discover -s instrumentation/tests -v`。也可以在项目已有依赖齐全的环境直接运行 unittest。
- little-coder 原有 `scripts/lc_smoke.py checks` 为 13 通过、1 个笔记裁剪检查失败；在修改前的上游版本已复现，不是这次新增失败。
- **尚未进行真实 Docker / H100 / Qwen 的端到端验证。** 现在证明的是本地逻辑和接口路径能走通，不是省时或提升成绩已经成立。
- 原版 Agent 或旧缓存若没报告主动停止原因，宿主机无法凭正常退出码推断“自然结束还是轮数耗尽”，会写未知；little-coder 新适配器明确上报这些原因。
- 测试数量目前只解析明确的文本汇总。`BUILD SUCCESSFUL` 不等于“确认跑了测试”；读不出数量会保留未知。这次没有修改 Java 测试启用方式，也没有更换基准题目或辅助文件。
- 明确的零测试结果会在记录卡中标为 `invalid_no_tests`，但旧的 `eval_result` 仍保留原口径。不能用旧评分字段来声称已经修好了零测试假通过。
- 模型时间来自已完成请求的记录，不是独占 GPU 计算秒数；排队、并发可能影响它。代理记录只按 run/node/task 和请求时间窗口归属，未完成请求、绕过代理的调用、并发重复执行同一题的精确归属仍可能未知。没有记录不填成零；回放不重复算成新模型调用。
- 记录卡能说明观察到了什么，不能凭末尾几行日志确诊所有错误。宿主机进程被强行杀死时，可能只留下一张未完成的卡，不能保证执行最终收卷。
